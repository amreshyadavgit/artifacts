Shukhee Integration Map

Every Bearer token in this flow does a different job. One authenticates a caller to shukhee_integration's own endpoints; a completely separate one authenticates shukhee_integration to the real Shukhee (SSK) vendor. This page traces both, plus the booking, polling, and app-dependency shape around them.

inbound — caller → shukhee_integration outbound — shukhee_integration → Shukhee Phase 1 — unverified local decode Phase 2 — verified via auth-service

01 · Topology

App dependency graph

spice_next_core (renamed from uhis_next_core) owns the shared auth primitives — auth.decorators, the Provider doctype, UHIS Settings. shukhee_integration and leapwell_telemetry both declare it as a required_apps dependency and import from it directly; nothing about the rename touched shukhee_integration's own module name or API paths. uhis sits on top as the client-facing umbrella, requiring all three.

02 · Inbound auth

Caller → shukhee_integration

Every endpoint in consultation.py is declared @whitelist(methods=["POST"], remote_auth=True). That wraps require_remote_auth (in spice_next_core/auth/decorators.py) under Frappe's own guest-accessible whitelist — the gate is a caller-supplied X-Auth-Token header, never a Frappe session cookie.

Sequence — X-Auth-Token validation

sequenceDiagram
  autonumber
  participant C as Caller (mobile / desk)
  participant EP as consultation.* endpoint
  participant RA as require_remote_auth
  participant JV as JWTTokenValidator
  participant AS as Legacy auth-service
  participant LOG as Remote Auth Activity Log

  C->>EP: POST shukhee_integration.api.consultation.*, X-Auth-Token: Bearer token, tenantId
  EP->>RA: wrapped call
  RA->>JV: extract_user_id(token, tenant_id)
  alt remote_auth_url unset — Phase 1
    JV-->>RA: decode sub claim, signature unverified
  else remote_auth_url set — Phase 2
    JV->>AS: POST Authorization: Bearer token, tenantId, client tag
    AS-->>JV: 200 userDetail.username, or 4xx/5xx
    JV-->>RA: username, or JWTDecodeError
  end
  RA->>LOG: enqueue Success or Rejected, async
  alt token invalid
    RA-->>C: 403 AuthenticationError
  else token valid
    RA->>EP: frappe.local.remote_user_id set, call the real endpoint
    EP-->>C: 200 result
  end

_current_provider() then matches the resolved id against Provider.username — deliberately not Provider.user, which is an unrelated Frappe User link.

ModeTriggerVerificationUsed by
Phase 1 UHIS Settings.remote_auth_url empty None — base64-decodes the payload, reads sub. Any self-minted {alg:"none"} token is accepted. Postman collection; Desk client's _mint_dev_token
Phase 2 remote_auth_url configured Real — RemoteAuthClient posts the token to the legacy auth-service and trusts its response only Production mobile traffic

03 · Outbound auth

shukhee_integration → Shukhee vendor

A second, unrelated Bearer token: each UHIS Shukhee User record holds its own shukhee_username/shukhee_password. get_valid_token() caches the resulting access token in frappe.cache(), keyed per record, and every live call goes through _authed_request(), which retries exactly once on a live 401 before surfacing a real error.

Sequence — token cache, refresh, retry-once-on-401

sequenceDiagram
  autonumber
  participant SC as shukhee_client
  participant CACHE as frappe.cache()
  participant SSK as Shukhee SSK API

  SC->>CACHE: get shukhee_token colon UHIS Shukhee User name
  alt cached, not expiring within 30s
    CACHE-->>SC: access_token
  else expired or missing
    alt refresh_token cached
      SC->>SSK: POST /ssk/refresh
      SSK-->>SC: new accessToken / refreshToken
    end
    opt refresh missing or failed
      SC->>SSK: POST /ssk/login-v2, username + password
      SSK-->>SC: accessToken / refreshToken
    end
    SC->>CACHE: set token, ttl = decoded exp minus now
  end
  SC->>SSK: request, Authorization colon Bearer access_token
  alt 401 despite cache
    SC->>CACHE: delete cached token
    SC->>SSK: retry once with a freshly fetched token
    SSK-->>SC: response, or a real error surfaced to the caller
  else 200
    SSK-->>SC: response
  end

The exp-claim decode here is only bookkeeping for cache TTL — it is Shukhee's own token, never trusted for identity on our side.

04 · Booking flow

start_consultation, end to end

Both auth layers meet here: the inbound check (section 02) runs once, on entry; every step below then runs under the outbound token (section 03), reused across calls until Shukhee itself expires it.

Sequence — booking an instant call

sequenceDiagram
  autonumber
  participant C as Caller
  participant EP as start_consultation
  participant P as Provider / UHIS Shukhee User
  participant SC as shukhee_client
  participant SSK as Shukhee SSK API
  participant DB as Call Logs

  C->>EP: contact_number, reason, requested_speciality, medias optional
  EP->>P: resolve Provider by username, load an Active UHIS Shukhee User
  EP->>SC: find_or_create_shukhee_patient
  SC->>SSK: GET /ssk/patient-list, search contact_number
  alt patient found
    SSK-->>SC: existing patient
  else not found
    SC->>SSK: POST /v2/patient/person-patient-create
    SSK-->>SC: new patient, id sometimes missing
    opt id missing
      SC->>SSK: GET /ssk/patient-list, relist
      SSK-->>SC: patient id
    end
  end
  opt medias attached
    EP->>SC: upload_medias
    SC->>SSK: POST /ssk/medical-document/upload
    SSK-->>SC: file ids
  end
  EP->>SC: resolve_speciality_id
  SC->>SSK: GET /patient/emergency-request-specialities
  SSK-->>SC: match by title, case-insensitive, or first entry
  EP->>SC: book_instant_call
  SC->>SSK: POST /ssk/emergency-request/v3
  SSK-->>SC: transactionId
  EP->>SC: resolve_request_id
  SC->>SSK: GET /ssk/all-emergency-request, page 0 then the real last page
  SSK-->>SC: newest request, by createdAt
  EP->>SC: build_video_call_url
  EP->>DB: insert Call Logs, status pending
  EP-->>C: call_log, call_url, status

resolve_request_id's two-fetch shape exists because /ssk/all-emergency-request returns oldest-first and paginates — for a number with real history, the newest record can land past page 0.

05 · Status & docs

Polling, completion, and document download

get_consultation_status short-circuits once a call reaches a terminal state — no Shukhee call at all. While still in progress, a doctor assignment is surfaced on every poll, not only the completed one, so the connected screen can name the doctor early.

Sequence — status poll, doctor fields, prescription capture

sequenceDiagram
  autonumber
  participant C as Caller
  participant EP as get_consultation_status
  participant DB as Call Logs
  participant SC as shukhee_client
  participant SSK as Shukhee SSK API
  participant F as Frappe File, private

  loop every 4s until terminal
    C->>EP: call_log
    EP->>DB: load Call Logs
    alt already terminal
      EP-->>C: cached status and links, no Shukhee call
    else in progress
      EP->>SC: get_emergency_request
      SC->>SSK: GET /patient/emergency-request colon id
      SSK-->>SC: status, doctor, appointment
      opt doctor assigned
        EP->>DB: persist doctor_name, speciality, facility
      end
      opt status becomes completed
        EP->>SC: download_and_attach, prescription and invoice
        SC->>SSK: GET presigned, short-lived document URL
        SC->>F: save_file, is_private true
        F-->>SC: permanent slash files slash URL
      end
      EP->>DB: commit updates
      EP-->>C: merged status
    end
  end
  opt mobile client only
    C->>EP: download_document, call_log, doc_type
    EP->>DB: verify doc.uhis_user equals calling Provider
    EP->>F: get_content
    EP-->>C: base64 bytes and filename
  end

Shukhee's presigned links expire; download_and_attach fetches them once and re-hosts the bytes as a permanent private Frappe File, so later reads never race an expired vendor URL.

06 · Callers

Mobile app vs. Desk client

Same three endpoints, same inbound contract — but the token each caller presents comes from a very different place, and only one of them is production-ready.

CallerToken sourceAuth mode it works underDocument viewing
Flutter mobile app ApiClient.exportAuthToken() — the SK's real, already-authenticated session Phase 1 and Phase 2 — a genuine token, verifiable either way download_document — no session cookie to open a private file URL directly
Frappe Desk client script _mint_dev_token — self-signed, alg: none, from the linked Provider's user Phase 1 only — rejected outright once Phase 2 is turned on window.open(prescription_link) — a real browser session cookie already grants access
