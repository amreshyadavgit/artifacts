CI/CD mechanism

How a push to uhis becomes a running site

Two separate machines do two separate jobs. GitHub Actions bakes four apps' source code into one Docker image and ships it to GHCR. The container itself, the first time it boots, is what actually creates the Frappe site and installs each app onto it — nothing in CI ever touches a database.

Build time— app source enters the image (no site exists yet)
Runtime— the site is created / an app is actually installed onto it
image → site
Nothing above has created a database. The image only carries each app's source and a sites/apps.txt listing them — Frappe doesn't consider an app installed until bench install-app runs against a real site. That happens exactly once, the first time the container boots, inside the one-shot program traced below.

Key details worth remembering

Idempotent by design
site-setup.sh checks sites/<name> and bench list-apps before creating or installing anything — a container restart after the first successful boot is a no-op past those checks.
One-shot, not autorestarted
site-setup runs at supervisord priority 20 with autorestart=false; a completed run stays EXITED(0) instead of looping forever.
The marker file is the gate
backend, websocket, worker and scheduler (priority 30) each independently pipe through wait-for-site.sh, polling for .site_setup_complete before exec-ing their real process — none of them assumes migrate has already run.
Safe to always migrate
This image is deliberately single-instance, so running bench migrate and clear-cache unconditionally on every boot never races a concurrent replica.
